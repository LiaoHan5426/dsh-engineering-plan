> 原型文件：`engineering-workbench.html`（单文件，无外部依赖，双击即可打开）

## 1. 怎么评审

1. 双击 `engineering-workbench.html`（或 `preview-layouts.html` 看三布局）。
2. 右上角「场景」下拉切换六个示例状态；顶部「宽屏 / 聊天 + 工作台 / 窄侧栏」切布局；「浅色」切明暗主题。
3. 底部「演示」条点「开始演示」，按 6 步走完 `描述需求 → 阅读规划与原型 → 提出修改 → 人工批准 → 查看执行 → 审核证据 → 确认交付`。
4. 顶栏一直挂 `DEMO` 徽章，提醒当前是原型而非真实数据。

示例业务：**为内部系统增加角色与权限管理（CHG-001 / feat/rbac-core）**，7 个任务、22 条验收、3 个并行轨道。

## 2. 四个视图

### 2.1 开发规划（`shot-plan.png`、`shot-light.png`）

- 首屏给出：研发目标、当前阶段（规划中 / 待评审 / 执行中 / 待交付 / 已交付）、方案版本（v1.2）、方案完整度（83% · 5/6 ready）、评审人、分支、任务规模。
- 方案完整度展开为六项：需求 / 代码分析 / 技术架构 / 接口与数据库设计 / 任务分解 / 验收标准，每项可展开读全文，未完成的项显示「Agent 正在补全」的进行态。
- 「评审要求」区只列需要人判断的事：评审范围、待确认项、最近一条评审意见。
- 涉及 UI 的方案提供「查看原型预览」入口（抽屉内是页面原型 + 设计说明 + 页面清单），并用 `v1.2` 标注它属于哪个方案版本。
- 意见框支持按页面/章节写修改意见 → 提交后生成 v1.3 草稿（原型里用 toast + 版本号变化表达，见 `#opinionBox`）。

### 2.2 架构设计（`shot-arch.png`）

- 模块边界：4 个模块卡（DOMAIN / APP / INFRA / WEB），每张写职责、依赖方向、对应目录。
- 分层架构图与右侧编号条目一一对应（① Controller ② Application Service ③ Permission Domain ④ Infra），文字与图互相锚定。
- 时序图、数据流图以折叠块承载，默认收起；源码编辑、完整 ADR、历史版本都在「按需展开」区，避免首屏噪音。

### 2.3 任务看板（`shot-board-executing.png`、`shot-board-blocked.png`）

- 七列：可开始 / 执行中 / 验证中 / 待人工审核 / 阻塞 / 已完成 / 已取消，单行横向排列，列宽固定，超出宽度横向滚动。
- 统一状态筛选（chips）+ 列表/看板切换 + 搜索（任务编号 / 目标 / 文件）。
- 任务卡按评审关心顺序排：编号 + 状态 → 目标 → 交付文件 → 验收进度 → 执行器与时间；失败任务在卡内直接显示失败原因（黄条）。
- 操作按状态出现：待人工审核卡给「确认完成」；已完成卡给「查看成果」；阻塞卡给「查看阻塞原因」。不会出现同一任务两处确认入口。
- 已取消任务单独一条轻量行（不计入交付门禁），不占看板列。

### 2.4 质量门禁（`shot-gate-executing.png`、`shot-gate-awaiting.png`、`shot-gate-ready.png`、`shot-delivered.png`）

- 顶部四个计数：验收总数 / 通过 / 失败 / 缺证据 / 待人工审核任务数，点标签即筛选矩阵。
- 验收矩阵按任务合并：同一任务的验收标准、结果、证据同排，结果靠右对齐，证据编号紧跟；人工确认列在该任务首行只出现一次，并写明「确认范围：T-102 · RBAC 数据表迁移 · 4 条验收」。
- 失败（红）、缺证据（黄）、待人工审核（橙）可直接从标签跳到对应行。
- 底部交付条：左侧是门禁结论与备注输入，右侧是唯一确认按钮。不满足条件时按钮禁用并给出具体原因（「还有 1 个任务待人工审核（T-102），1 个任务阻塞（T-106），另有 1 项未满足」）。
- 交付后进入锁定态：状态变「已交付」，交付条变成确认人 / 时间 / 版本 / 验收条数，按钮变灰「已交付」，已取消任务行注明「不计入交付门禁」。

## 4. 交互、状态转换与异常处理

**主链路（演示条 6 步）**

1. 描述需求 → 「让 Agent 生成规划」→ 场景 `empty`，只有空态卡与主按钮。
2. 生成完成 → `review`：完整度 83%，六项中「接口与数据库设计」在补全，其余 ready。
3. 提出修改 → 在意见框写「原型里任务卡要能看到验收进度」→ 提交后生成 v1.3 草稿，v1.2 保持可回看。
4. 人工批准 → 版本锁定，任务从「可开始」按依赖开始启动（`executing`）。
5. 查看执行 → 看板出现执行中 / 验证中 / 阻塞 / 待人工审核四类卡；点卡片进任务抽屉（目标、交付文件、验收标准、证据时间线、失败原因与建议）。
6. 审核证据 → 门禁矩阵里逐条看结果与证据编号；`awaiting` 场景下矩阵里点「确认这 4 条验收」。
7. 确认交付 → `ready` 场景下交付条可点 → 二次确认对话框（版本 / 验收数 / 失败 / 缺证据 / 任务数）→ 锁定态。

**异常与保护**

- 交付条件不满足：按钮禁用 + 明确原因，不弹无信息提示。
- 后台读取 / 场景切换期间点页签：提示「正在切换场景或提交中，请稍候再切换视图」，不静默吞掉点击。
- 未保存的意见 / 交付备注：切换场景或关闭抽屉前提示；草稿保留在原处。
- 已取消任务：单行展示并标注不计入门禁，避免被误当作阻塞。
- 失败任务：卡片内黄条给出具体失败断言，抽屉里再给建议动作。
- 焦点：所有按钮、页签、卡片可 Tab 到达，`:focus-visible` 有 2px 描边；抽屉/对话框打开后焦点进入，Esc 关闭。

## 5. 与现有实现的对应关系

| 原型元素 | 现有实现 | 说明 |
|---|---|---|
| 四个视图页签 | `client.js:868` `const TABS = ["plan","design","tasks","resources"]` | 一一对应，原型只换了标签文案（开发规划 / 架构设计 / 任务看板 / 质量门禁） |
| 任务状态徽章 | `client.js:752` statuses：pending / running / verifying / awaiting-review / blocked / failed / completed / cancelled | 原型的七列是同一套状态的看板分组，未新增状态 |
| 看板七列 | `readyTasks`（reasons：DEPENDENCY_BLOCKED / APPROVAL_REQUIRED / FILE_CONFLICT / ACTIVE_RUN / UNRESOLVED_UNKNOWN）+ `task.status` | 列 = 状态；「可开始」= readyTasks 里 dispatchable 的任务 |
| 验收矩阵 | `gateStatus`（blockers：APPROVAL_REQUIRED / ACTIVE_RUN / UNRESOLVED_UNKNOWN / TASK_NOT_TERMINAL / NO_COMPLETED_TASK，warnings：NO_SUCCEEDED_COMMAND） | 矩阵的数据就是 gateStatus + 每个任务的 acceptanceCriteria/evidence |
| 交付条与确认 | `acceptDelivery`（人工专属）+ `deliveryNote` 词条（`client.js:387`）+ 交付对话框 | 原型把「说明为什么不能交付」显式化，契约侧只需把 blockers 翻成文案 |
| 人工确认按钮 | `transition` 到 `completed`（用户身份直通；agent 身份被 `src/core.js:776` 改写为 awaiting-review） | 原型里「确认完成 / 确认这 4 条验收」都对应这一条动作 |
| 意见与版本 | `replan`（人工专属）+ 方案版本（planVersion） | 原型新增的是「按页面/章节定位意见」，落库方式需扩展 |
| 只读查询 | `list / get / gateStatus / readyTasks / context / export`（经 `ctx.remote.commands.execute`） | 原型不引入新的读通道；后台刷新仍走命令通道但静默渲染 |
| 变更切换 | `engineering-planner:workbench` 侧栏 + 变更列表 | 原型把变更条压成一行，切换不离开当前视图 |

## 6. 需要新增的能力（原型中已标注，后端未支持）

1. **按页面/章节定位的意见**（`plan.opinions[]`：`{sectionId, pageId, text, author, version}`）——现有只有整份规划的 `replan`。必要，因为「针对页面提意见」是评审的主路径。
2. **方案版本化的 UI 原型产物**（`plan.prototypes[]`：`{pageId, title, htmlPath, screenshotPath, version}`）——原型抽屉现在用内置示例，真实实现需要一个存放页面原型/截图的字段与静态资源路径。
3. **任务级阻塞原因聚合**（`readyTasks` 目前给 reason 码，看板卡需要一句话文案 + 关联任务）——现状要客户端自己拼，建议后端在 `readyTasks` 返回里带 `reasonText`。
4. **按任务范围的人工确认记录**（`evidence` 已有 passed 记录，但「谁在什么范围确认了 4 条」没有独立对象）——门禁矩阵要在人工确认列写清范围，需要一条 `confirmations[]` 记录。
5. **交付锁的读模型**（`delivered` 后的确认人/时间/版本/验收数快照）——`acceptDelivery` 会写状态，但界面要展示快照，建议在 `get` 里直接给出。
6. **场景/演示数据开关**（仅原型需要，真实实现不必落地）。

## 7. 分阶段重构清单（优先复用现有能力）

**阶段 0 · 零契约改动（可立即做）**
- 四视图改名 + 页签顺序对齐原型；变更条压成一行。
- 看板改为七列横向 + 列宽固定；卡片字段顺序按「目标 → 交付文件 → 验收进度 → 执行器」重排。
- 门禁矩阵按任务合并行、结果靠右、证据编号紧跟；把 `gateStatus.blockers` 翻成中文原因文案。
- 交付条：禁用态显示具体原因（复用现有 blockers），确认按钮唯一化。
- 工具条单行、chips 细滚动条、看板列拉伸填满、toast 不压交付条（本轮原型里已验证的样式改动）。
- 只读刷新保持现有静默渲染（`QUIET_ACTIONS` + 读缓存），不新增命令调用。

**阶段 1 · 小契约扩展**
- `readyTasks` 增加 `reasonText`（服务端一句话解释）。
- `get` 增加 `delivery` 快照（确认人 / 时间 / 版本 / 验收条数）。
- 任务抽屉的「证据时间线」用现有 evidence + verificationRuns 组合即可，不需新接口。

**阶段 2 · 中等改动**
- 意见对象（`plan.opinions`）与按章节定位：`replan` 接受 `opinions` 输入，生成新 planVersion 草稿。
- 按任务范围的人工确认记录（`confirmations[]`），门禁矩阵人工列读取它。

**阶段 3 · 需要设计决策**
- 方案级 UI 原型产物（存放位置、版本绑定、截图来源）；决定是走工作区静态文件还是宿主资源。
- 交付锁的完整读模型与导出（`export` 带交付快照）。

## 8. 本轮已修的原型缺陷

| # | 缺陷 | 处理 |
|---|---|---|
| 1 | 看板工具条换行，右侧留大片空白 | 工具条强制单行，chips 区可横向滚动 |
| 2 | chips 滚动条是系统白色粗条 | 改为 4px 深色细条 |
| 3 | 交付条原因文字把按钮挤到换行 | 原因右对齐、按钮独立不换行 |
| 4 | toast 压住交付条 | toast 上移 `calc(var(--demo-h) + 104px)` |
| 5 | 完整度显示 82% 与「5/6 ready」矛盾 | 按 5/6 改为 83%，其余场景按 6/6 显示 100% |
| 6 | 看板列高度不足，下方大片留白 | 列等高拉伸，宽屏/并排下铺满可用高度 |
| 7 | 场景切换中点击页签静默无响应 | 改为 toast 提示「正在切换场景或提交中」 |
| 8 | 中文按钮逐字折行（生成物通病） | 关键按钮 `flex:none; white-space:nowrap` |
| 9 | 已取消任务长文本把页面撑出横向滚动 | 单行省略 + 查看入口 |
